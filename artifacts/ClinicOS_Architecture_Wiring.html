ClinicOS · program-level architecture

Every file the consultation touches, in the order it touches it

One codebase runs two ways: on a clinic's own computer against a SQLite file, and online against Postgres as a service many clinics share. What follows is the wiring — screen, route handler, library, table — for each thing a clinic actually does, with the rules that are enforced in code rather than in the interface.

rule
One SQL for two databases. ? placeholders, every capitalised identifier double-quoted ("Consult", "patientId"), CAST(COUNT(*) AS INTEGER), LOWER() instead of COLLATE NOCASE, ISO strings and 0/1 flags. A missed quote returns patientid on Postgres and nothing on SQLite.

Record → transcribe → draft → sign → print

The doctor gets about two minutes per patient. ClinicOS records the consultation that was already happening and asks only for a review and a signature. Four steps in one component, each backed by its own route so a crash mid-visit loses nothing.

invariant 1
No clinical judgement. No diagnosis generation, no risk scores, no triage badges, no "needs attention" flags. Software that stores, formats and communicates data sits outside CDSCO device regulation; software that quantifies a physiological parameter to drive a decision does not. Raw numbers and trends are shown — the doctor sets any flag. followUpOn and returnIf are never filled by the model.
04

Review and edit

The doctor's edits go somewhere else entirely from the draft. The gap between the two is the only honest accuracy measure this project has.

componentConsultWorkflow.tsx

Plus Favourites.tsx — the doctor's own saved plans, applied without overwriting anything written.

hooksrc/lib/useAutosave.ts

Debounced save to the server and a localStorage mirror.

routePUT …/note

Writes only the working copy.

columnConsult.workingJson

Favourite holds the plan only — never a complaint, history or finding.

invariant 6
draftJson is immutable once written. It holds the model's original output; edits go to workingJson. Never overwrite one with the other. A note written by hand has no draft at all — draftJson stays NULL, signing logs no Edit rows, and it counts in neither "time saved" nor "edits per note".
05

Sign — and the recording goes

Signing is the one irreversible moment in the flow. It writes the diff, sets the follow-up date, and deletes the audio.

→ signConsult() in db.ts, inside one transaction.

tableEdit

One row per field the doctor changed — the accuracy metric.

The date copies to Consult, which is what the desk's Follow-ups list reads.

The recording is deleted here.

invariant 3
Audio is deleted when the doctor signs. Promised to every patient in the clinic's terms and enforced in signConsult(). Recordings never sync, and a visit signed on one copy deletes the other copy's recording of it when the signature arrives — mergeConsult() in sync.ts. Do not add audio retention. Never train on patient audio (invariant 4): the Pilot Agreement permits de-identified data only, with an opt-out.

Who may open what

Hiding a link is never the control. Every page calls requireUser() and every route handler calls requireApiUser() with the capability it needs — because middleware runs on the Edge runtime, where the SQLite driver cannot even load.

Admin's own surface

Backups

BackupPanel.tsx → /api/backup/* → backup.ts. A daily snapshot triggered lazily on page load, 14 kept, one-tap download.

  • Restore is behind a typed RESTORE, and snapshots the current database first.
  • A restore brings back the backup's accounts; if the backup predates accounts, the restoring admin is kept so /setup never reopens.
  • SQLite's online backup API, never a file copy — WAL mode means cp produces a file that opens fine and is quietly missing the newest consultations.

People

UsersAdmin.tsx → /api/admin/users/*. Add people, manage access, reset passwords. Usernames are unique within a clinic.

Activity log

(clinic)/admin/audit reads AuditEvent. Never write a patient's name into detail — a deleted record must not survive in the log.

Clinic identity & AI

ClinicSettingsForm.tsx, PrescriptionSettings.tsx, AiSettings.tsx → ClinicSetting via clinic.ts. .env is only the fallback, and only for the first clinic. ai_ keys never travel to a clinic computer.

Deletion

DeletePatient.tsx — type the patient's name. Anything irreversible requires typing something out; apply that pattern to any new destructive action.

Export

/api/backup/export and /api/patients/[id]/export. No lock-in (invariant 8): full export in an open format must keep working — 35 MB in about 800 ms on the bench clinic.

Two copies, one clinic

A clinic whose plan includes it keeps a full copy on its own computer, in step with its clinic online. The merge rules are the same code on both sides — which is the only reason the two copies can be trusted to agree.

02

Every minute, both directions

Triggers — not queries — mark what changed, so a clinic's wrong clock cannot lose a row.

modulesync-client.ts

Runs every minute. Never awaited by a page.

routesPOST /api/sync/push
POST /api/sync/pull

Plus /api/sync/share so a local signature can reach the patient portal.

markerssyncSeq · syncedAt · syncOrigin

A counter on SQLite, the database clock online, and an origin so a computer is never sent its own changes back.

mergemergeConsult() · mergeBill()

While merging, SQLite's triggers stand aside (SyncState.applying) and merged rows get syncSeq = -1.

easy to break
Adding a column to a synced table means adding it to COLUMNS in sync.ts, or it silently stays on one copy. A new table needs a decision about whether it travels at all. Settings travel only when the key starts clinic_ or rx_. Tombstone ids include the clinic (<clinicId>:<table>:<rowId>) — without it one clinic's computer could block another's real deletion.

What travels, and what never does

Travels

  • Patient, Consult, Edit, QueueEntry, Favourite
  • Bill, Recall, User, AuditEvent
  • ClinicSetting — only clinic_ and rx_ keys
  • SyncTombstone — deletions, so they land on both copies

Never travels

  • Recordings — and a signature deletes the other copy's too
  • ai_ settings, and the AI keys behind them
  • receipt_tag, so receipt numbers cannot collide
  • PortalShare's three secret columns
  • Sessions, device keys, operator accounts

Proven by

scripts/test/sync-test.cjs runs two clinic computers beside the online copy. On Postgres, test:e2e:pg starts two more copies of the same build on ports 3101 and 3102.

PGlite multiplexes every client over one session, so PG_POOL_MAX=1 there: its race tests prove correctness, not concurrency. Those are real only against Supabase.

What the patient gets

Online only, at /p. Exactly the signed prescription — never the transcript, the recording, the draft or the edits. Three languages, chosen on the first screen; the prescription itself stays as the doctor wrote it.

Tooling that has to pass

npm run test:e2e

Seeds a prototype-era database in .test-data/, builds against it, serves on :3100, and runs every suite over real HTTP.

  • perm-test — the capability matrix, every route
  • queue-test · workflow-test · billing-test · rx-test
  • tenancy-test — every route with another clinic's ids
  • sync-test — two clinic computers beside the online copy
  • portal-test · admin-tools-test

npm run test:e2e:pg

The same suites the way the online copy runs — under /app, with the setup code and clinic timezone — against PGlite, so nothing needs installing. TEST_DATABASE_URL points it at real Supabase for true concurrency; TEST_BASE_URL tests the deployed app itself.

Never point either at a database holding real records.

npm run bench

A throwaway clinic in .bench/ — 5,000 patients, ~10,000 visits — timed over HTTP. Nothing is fast because it is fast with twelve patients.

  • Today 154 ms · Patients 50 ms
  • A record 32 ms · Bills 33 ms
  • Follow-ups 79 ms · Clinic admin 225 ms
  • Whole-clinic export 800 ms for 35 MB

Traps worth remembering

  • Every db.ts function is async, and a missing await still compiles — recordAudit(...) may never run online.
  • await x().y awaits y. Write (await x()).y.
  • next build collects pages in parallel workers, each running the SQLite migrations — every statement must be safe to run twice at once.
  • Never test against data/. It is the clinic's real database. Use npm run dev:sandbox.
  • The website's headers() must skip /app, or its Permissions-Policy: microphone=() reaches the app and stops recording.

The gate that matters. Zero of the twenty doctor discovery interviews have been done. Week 4 asks whether ≥ 6 of 20 doctors name documentation unprompted among their top three frustrations. Building further features before those interviews is the main risk to this project.
